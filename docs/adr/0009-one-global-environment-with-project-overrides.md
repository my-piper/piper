# One Global Environment; Projects override or rebind its Variables

There used to be three Environments: the Platform Environment, which admins set for every user; one User Environment per user, shared by all of that user's Projects; and the Project Environment. Every Variable a Node declared also carried a scope (`global`, `user` or `pipeline`), which decided the order those Environments were searched in. A binding to a User Variable counted only when the Project's owner launched it. We kept two layers. The Global Environment (the former Platform Environment) is the only shared one. Everyone signed in can read it, but only admins edit it. A Node declares just the names it reads. Each of those names in a Project is either bound to a Global Variable (by default the one with the same name, or another the user picks) or overridden with the Project's own value.

We considered letting every user edit the Global Environment. Anyone who can edit a Pipeline can already read every Global secret from a script (ADR 0007), so limiting edits adds no confidentiality. We kept edits to admins anyway, so that one user can't break or redirect a key everyone else's Projects use. A user's own keys now belong on each Project that needs them.

## Consequences

- A user who kept a key in their User Environment for several Projects now sets it on each of those Projects. Since Projects are private (ADR 0008), a Project override is visible only to its owner and admins.
- A binding applies to every launch of the Project, including Deploy and Child Launches, whoever starts them. A Deploy freezes its overrides and what each binding points to, but reads the Global values when it runs, so rotating a Global key reaches running Deploys.
- Node scripts still receive `env.scope`, but its values are now `global` (the value came from the Global Environment) or `pipeline` (the Project's own value). Catalog scripts that checked for `user` to skip billing a user's own key must check for `pipeline` instead.
- The `scope` of a Node's declared Variable is no longer stored or validated. Older YAML that still carries it imports without error.
- `npm run cli -- env migrate-user-environments` (use `--dry-run` first) copies every User Variable that an owner's Project or Deploy used, whether inherited or bound, into that Project or Deploy as its own value. This includes Deploys under the owner's prefix whose Project is gone. It then deletes the User Environments and logs the names it dropped, plus each binding whose User Variable was missing. Such a binding was unset before, and now reads the Global Variable of the bound name if one exists. Nothing is merged into the Global Environment, and the step can't be undone. Run it right after deploying the new code. Until it runs, a declared name the Project doesn't set reads the Global Variable of the same name instead of the user's own.
